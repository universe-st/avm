# 御膳房 · 全流程实测记录（2026-10-31）

用户要求：**完整玩一遍 `intro → explore → gate → hide → pair → follow → haystack → done`，把素材、流程、交互、文字的问题一并修掉。**
本文只记「复现到的问题 → 根因 → 修法 → 复验」，不记录设计意图（那是 `DESIGN-CH01-EXPLORE.md` 的事）。

## 1. 致命：在屏风里永久卡死（软锁）

| 项 | 内容 |
| --- | --- |
| 现象 | 按提示躲进屏风 (18,6) 后，**任何方向键都不动**；9 秒窗口到点判负，看起来像「按键失灵」。 |
| 根因 | `PLAYER_FOOT = { width: 56, height: 18, padding: 8 }` 是按寝室 21.8px 格子调的，实际脚盒宽 56+2×8=**72px**，比御膳房的 64px 一格还宽。屏风西边紧贴挡路柱 `(17,5)-(17,6)`，玩家被 `enterHide` 瞬移到格心后脚盒压住柱子，`canStandAt` 对**每个方向的目标点**都是 false → 上下左右全判死。 |
| 修法 | ① 新增 `KITCHEN_PLAYER_FOOT = { width: 44, height: 16, padding: 4 }`（52px < 一格），厨房场景改用它；② `moveWithCollision` 加「脱困兜底」：当前位置已非法时放行移动，一旦合法立刻恢复严格判定。 |
| 复验 | `test/map-collision.test.ts` 新增 3 条：屏风格用寝室脚盒站不住 / 用厨房脚盒站得住且能挪动 / 非法位置不会硬锁。手动复玩：屏风内可自由出藏、跟随、跑草堆。 |

## 2. 致命：结束卡一出现就被自己点掉，看不到结尾

| 项 | 内容 |
| --- | --- |
| 现象 | 老肯被偷袭、最后一句「老麦：走了，传膳去」念完，画面**没有结束卡**，直接回到探索、目标变回「摸清御膳房」。失败卡同理（一弹出就「再进去」）。 |
| 根因 | Compose 的键盘导航把 `Space`/`Enter` 映射成 `activate`（`vendor/.../nav.ts` 的 `keyboardActionOf`）。玩家用 Space 推进对话，`finishDialogue()` 在**同一个 keydown** 里弹出结束卡，UI 场景的键盘源随后把这次 Space 交给 `focusFirst` 刚聚焦的「重开本节」→ 结束卡瞬间被点，`scene.restart({retry:'explore'})`。 |
| 修法 | 新增 `src/ui/modal-guard.ts` 的 `MODAL_NO_AUTOFOCUS = { autoFocus: false }`，铺到 `kitchen-modals`（失败卡/结束卡/退出确认）、`ch01-modals`（第一章结束卡）、`battle-ch01-modals`（战斗开场/战败）——弹窗里没有控件持焦点，`activate` 直接返回 false；指针点击与 Tab 进入照旧。 |
| 复验 | 结尾对话后连按 2 次 Space，`phase` 仍是 `done`、`endCard` 仍在（`acc-end.png`）；失败卡上按 Space/Enter 不再触发重开，点「再进去」才 `retried=true` 并回到 `explore`（`ch01-kitchen-fail-390.png`）。 |

## 3. 老麦/老肯站在墙里，门卫站在旁边却看不见

| 项 | 内容 |
| --- | --- |
| 现象 | 门一开，台词说「两个人跟着进来」，画面上什么都没有；门卫就在两步外也完全不可见，玩家被「看不见的东西」抓住。 |
| 根因 | ① `openGate()` 把两人 `setPosition` 到 `(14,3)/(16,3)`，而 row 0-3 是整条实墙；② 角色可见性只看「该格是否在**玩家视锥**里」，老麦进门时在玩家身后、门卫在侧后方，都不在 120° 锥内 → alpha 恒 0。 |
| 修法 | ① 站位改到走道 `(15,4)/(16,4)`，老肯走 `(16,4)→主道` 并入队；② 新增 `npcSeen(at)`：视锥命中 **或** 距离 ≤2.5 格且有视线就显示——贴脸站着的人不可能因为你朝别处看就整个消失；`KitchenEnemy` 与 `PairActor` 都改用它。 |
| 复验 | 门开后老麦/老肯在走道上淡入，门卫红眼机器人在玩家右手边可见（`ch01-kitchen-in-screen-390.png`）。 |

## 4. 第二幕目标写着「躲起来」，但屏风那一片是黑的

| 项 | 内容 |
| --- | --- |
| 现象 | 从下方摸到传膳门，屏风一带从未进过视野，两态迷雾下是纯黑；玩家既看不到屏风也不知道往哪躲。 |
| 根因 | 迷雾「未探索=纯黑」+ 门触发点在南侧，`openGate()` 没有补亮目标区域。 |
| 修法 | `openGate()` 里 `revealAround(18, 6, 2)` 并立即刷新视野；`updateNear` 在 `phase==='hide' && !hidden` 时于屏风上方钉 `[E] 躲到屏风后`（`hideHintText`），进藏即隐藏。第三幕同理：`onPairAtStove()` / `startKenSearch()` 照亮草堆周围 3 格。 |
| 复验 | 躲藏窗口内屏风与提示都可见（`ch01-kitchen-hide-window-390.png`）；草堆目标出现时草堆已在视野里（`run-08-hay-objective.png`）。 |

## 5. 4 秒躲藏窗口实际拿不出来

| 项 | 内容 |
| --- | --- |
| 现象 | 门一开就倒计时 4 秒，绝大多数情况直接「被发现了」，连方向都没定。 |
| 根因 | 屏风在挡路柱 `(17,5)-(17,6)` 东侧，从门触发点过去要「上到 row 4 → 东移 → 下到 (18,6)」，直线 3 格实际走 7 格（≈3.2s 纯移动），而玩家同时还要辨认新出现的两个 NPC 与红视锥。 |
| 修法 | `HIDE_DEADLINE_MS` 4000 → 9000；催命感交回门轴声、心跳与红色视锥。设计文档 §3.2 同步改写并记录理由。 |
| 复验 | 按「上 1.0s → 右 1.3s → 下 0.62s → E」能以 ~5s 余量进藏。 |

## 6. 老麦一路甩开玩家，灶台台词在十几格外播

| 项 | 内容 |
| --- | --- |
| 现象 | 跟随幕一开始，老麦 100px/s 直冲灶台，玩家 140px/s 也追不上（走走停停）；「这锅有人动过吧？」在屏幕外播完，玩家只看到目标变了。 |
| 根因 | `pairMai.walk(整条路径)` 一次走完，没有任何「等玩家」的语义。 |
| 修法 | 改成**逐段推进**：走完一个拐点就停住，玩家进入 4.5 格才继续下一段；停下时老麦头顶挂「跟上来」（`pairWaitText`）。老肯始终落后一个拐点。走速 105。 |
| 复验 | 灶台对话稳定发生在玩家 2 格以内（`run-07-stove.png`）。 |

## 7. 第三幕赛跑是必输局

| 项 | 内容 |
| --- | --- |
| 现象 | 灶台台词念完，老肯已经走到草堆；玩家从灶台到草堆 15 格，几乎每次都被抓。 |
| 根因 | 老肯 100px/s 走 14 格 ≈ 9s，玩家 140px/s 走 15 格 ≈ 6.9s，但对话在灶台结束，玩家还要先认出草堆在哪，且小白的「橱柜 15.68%」是**故意误导**（躲柜子必被发现）。 |
| 修法 | 老肯先犹豫 `KEN_SEARCH_DELAY_MS = 1600`；搜索速度降到 `KEN_SEARCH_SPEED = 82`；草堆周围 3 格提前照亮。 |
| 复验 | 按正常走位进草堆后 `hidden='hide.hay'`、老肯到点 `haystackReady=true`、`[J]` 偷袭可用（`ch01-kitchen-haystack-390.png`）。 |

## 12. 已知遗留（未改，记录在案）

1. **地图美术与碰撞有 ~1 格错位**：库房与传膳廊之间，art 的砖地在 col 13 就开始，ASCII 把 col 12-13 都算墙。只影响贴墙手感，不造成卡死；改 ASCII 要重切整张 32×64，风险大于收益。
2. **橱柜的误导是设计**：小白按「被发现概率」推荐橱柜，但老麦会补「柜子也看看」——这条是叙事陷阱，不是 bug。
3. **跟随幕没有「跟丢了」失败**：老麦会等人，最坏情况是原地不动，不会判负。等第三幕正式接入巡逻联动后再评估。
4. `docs/screenshots/ch01-kitchen-b4-gate-390.png` 是修复前的旧图（只有名牌），新的对应图是 `ch01-kitchen-in-screen-390.png`。
5. **横屏（1200×648）不成立**：`planViewport` 只做竖屏设计（720×1280-1600），横屏下 `scale` 被钳到 1.75、画布 1260×2240，可见的只有中间一条；寝室/宫廷同样如此，不是本节引入。本节验收按用户要求只走 390×844。
6. **未探索格是纯黑，容易被误读成「背景没抠掉」**：这是两态迷雾的既定表现（`DESIGN-CH01-EXPLORE.md`），不是素材残留。已核过：24 张厨房角色 PNG、6 张图标、8 张行走 webp 都没有不透明白底；地图 `kitchen.png` 是整图不透明背景（本来就该是不透明）。
   如果观感上仍像「洞」，下一步应改表现（未探索改成近黑蓝 + 边缘柔化），而不是再抠一遍图。

## 14. 地图重做：放大 1.5× + 墙有高度（2026-10-31 追加）

用户反馈：「感觉地图应该整体放大，这种墙不如人高导致人身体一半在无视野区，很影响体验。请重新设计地图。」

### 14.1 三条根因（都不是同一个问题）

| 现象 | 根因 |
| --- | --- |
| 人的头/上半身整块变黑 | **图层顺序 bug**：`LAYERS.fog = 2500` 而 `characterDepth()` 上限只有 1900 → 迷雾画在角色**上面**。角色 245px ≈ 3.56 格，脚所在格以北 3 格只要没探索，黑幕就把上半身吃掉。 |
| 墙不如人高 | 分区边界墙带只有 **1 格厚**，墙面无处可画；`compose-kitchen-map.py` 把墙顶逐格平铺，没有高度。 |
| 地图该整体放大 | `tileSize 64` 下一屏 11.25 格，角色 3.56 格 —— 2.5D 里 2–2.5 格才正常。 |

### 14.2 改了什么

1. **迷雾下移**：`LAYERS.fog 2500 → 500`（在 `markers` 之上、`characters` 之下）。角色永不被雾切；敌人隐蔽本来就靠 `npcSeen()` + 180ms alpha，不靠雾盖人。
   `test/render-layers.test.ts` 加了「雾永远低于角色」的断言，并把 `characterDepth(4096) < fog` 翻成 `> fog`。
2. **放大 1.5×**：`tileSize 64 → 96`，设计 2048×4096 → **3072×6144**；美术重出为 **1536×3072（48px/格）** 并改存 **WebP q88**（PNG 5–6MB → WebP 0.69MB）。
   所有 px 速度 ×1.5（步行 140→210、潜行 80→120、跑 230→345、老麦 105→158、老肯 82→123），**格/秒不变**，追逐与赛跑的松紧和调校时一致。
   `KITCHEN_PLAYER_FOOT 44/16/4 → 66/24/6`（78px，仍 < 一格）；交互半径 ×1.5；相机 deadzone 120×180 → 180×270。
3. **墙带加厚到 2 格**（行 15 / 25 / 48 各复制上一行的墙带，**行号不移动**，所以全部 tile 坐标不用重排）。
   `compose-kitchen-map.py` 对每格墙判断「南邻是否可走」：可走 → 画**立面**（压暗 46% + 两道砖缝 + 墙脚接缝阴影），否则画**顶面**。于是每段横墙都是「顶面 + 立面」，96px 一格下墙带高 192px，外圈 4 格墙 288px > 角色 245px。
4. **迷雾边缘柔化**：贴着已照亮格子的那一圈用 α0.72，里层 α0.94；`ambientRange 1.5 → 2.5 格`，人身边始终有一圈亮地。
5. **门牌小字撤掉**：屏风/传膳门/橱柜/后门现在有清楚的形状，18px 小字在 96px 格上像误笔；区域名与地标字号 ×1.5 保留。

### 15.6 「怪还是比主角小」的根因与修法（2026-11-01 追加）

`make-static-sprite.py` 归一化时是**高度和宽度双重约束**的：目标高 371，但内容宽超过帧宽 160 时会改按宽度缩（"宁可矮不能瘦"）。
主角身形细长（宽高比 0.35）正好撑满 371；御膳房这几位偏胖，于是被宽度卡矮：

| 角色 | 帧内实际身高 | 占 371 的比例 |
| --- | --- | --- |
| 主角 | 371 | 1.00 |
| 老麦 | 349 | 0.94 |
| 门卫 | 324 | 0.87 |
| 老肯 | 293 | **0.79** |
| 御厨 | 269 | **0.73** |
| 太监 | 371 | 1.00 |

所有 sprite 的 `scale` 都是 0.6138、`displayHeight` 都是 246，**看起来一样大，实际身高差 27%**。

修法：`KITCHEN_CAST` 每个角色带 `heightRatio`，渲染缩放改成
`0.6138 × 1.04 / heightRatio`（1.04 = 成年人比主角高 4%）。标签/警戒符的 Y 偏移同比例放大。
修完实测：主角 228px，其余四人 235–238px，肉眼已看不出谁小。

| 角色 | down | up | left | right | 45° |
| --- | --- | --- | --- | --- | --- |
| 御厨 | 269 | 285 | 366 | 371 | 272–295 |
| 老肯 | 293 | 300 | 343 | 371 | 276–281 |
| 门卫 | 302 | 371 | 371 | 324 | 302–320 |

### 18. 转向方向反了 / 一走动就变矮（2026-11-01）

**① 一走动就变矮** —— 真 bug，所有角色都有。
行走 sheet 是从**另一段视频**抽的，姿态幅度大、宽度更容易超帧，被宽度约束压得比静态图更矮
（御厨 down：静态 269 → 行走帧中位数 190，差 30%）。之前统一按静态身高算缩放，所以一迈步就缩水。
修法：`KITCHEN_CAST` 再加 `walkHeightByDir`（20 帧中位数），`castScale(cast, dir, walking)` 分开算；
sheet 抽坏（行走身高 < 静态 55%，角色走出画面那种）则退回静态身高。
验证：御厨 down 静态 269×0.881=237、行走 190×1.246=237，一致。

**② 看向的方向和视野方向相反** —— 不是代码 bug，是素材被镜像了。
用「头部皮肤重心相对头宽的偏移」量化判据：
| 角色 | left | right | 结论 |
| --- | --- | --- | --- |
| 御厨 | −0.16 | +0.19 | 正常 |
| 老肯 | −0.13 | +0.14 | 正常 |
| 老麦 | −0.03 | +0.00 | 侧面几乎是正面，转向不明确 |
| 门卫 | **+0.37** | **−0.08** | **左右对调** |
| 太监 | 测不到（肤色太淡） | — | 目视 left 是背面 3/4 |

门卫的转圈视频整体镜像了，静态和行走都跟着反。给 `KITCHEN_CAST` 加 `dirAlias`（逻辑方向 → 实际用哪张图），
门卫左右及四个斜向全部对调，静态/行走/身高查表都走同一张别名。

顺带补：老麦 `walk_left` 那份 sheet 抽坏了（角色走出画面，帧高只有 160），用 `walk_right` 水平镜像重建了一份。

### 18.1 门卫朝向根治（2026-11-01 下午）

`dirAlias` 只是把两张错图换位置，治标。根治办法比想象便宜：**转圈视频本身就是完整 360°，错的只是截帧下标。**

做法：
1. 把 `turn/frames/` 的 32 张候选帧全扫一遍，用「头部皮肤重心 / 头宽」当判据输出曲线：
   ```
   0 -0.00 ... 14 -0.15 | 15-22 无脸（背面）| 23 +0.15 ... 31 +0.01
   ```
   曲线一眼看出这段视频是**逆时针**转的，而默认截帧下标是按顺时针写死的（front=0 / right=8 / back=16 / left=24），所以左右整体反了。
2. 用 `setTurnPick` 把八个方向重新指到正确下标：front=0 · downRight=27 · right=23 · upRight=21 · back=18 · upLeft=16 · left=14 · downLeft=7，再 `cutTurnFrames` 重切。**免费，不用重跑视频。**
3. 但行走视频是**用旧静态图当首帧**生的，六段侧向跟着错，必须重跑那六段（`runVideos({keys:[...], regenerate:true})`）；正向/背面两段不用动。
4. 重跑后八向闭合误差 1.5–3.7，全部无告警。`walk_left` 又抽坏了（帧高 160），用 `walk_right` 镜像重建。
5. 删掉 `dirAlias`，`heightByDir`/`walkHeightByDir` 按新图重测。

结论：**转圈截帧的默认下标假设顺时针；模型给逆时针时，只调 pick 就能修朝向，千万别急着重跑视频。**

顺带核实：老麦的默认下标本来就是对的（f0 正 / f4 右下 / f8 右 / f12 右上 / f16 背 / f20 左上 / f24 左 / f28 左下，目视确认）。之前用皮肤重心测出"±0.03 没转"是他的脸涂了白粉底、皮肤检测失效导致的**假信号**，不是素材问题。

### 20. 行走时变胖（2026-11-01 下午）

用户：「感觉行走的时候怪变胖了又」。承自 §18：当时按"身高"补偿行走帧，
而行走帧比静态图矮（御厨 down 269 vs 371），把矮的拉到 371 就必然**横向同比放大 → 变胖**。

根因有两层：

1. **帧宽 160 太窄**：静态图被宽度卡住（御厨 down 只有 269 高）。放宽到 **224** 后，
   八个方向静态图全部回到 371，这个维度彻底消失（`make-static-sprite.py` 新增 `--frame-size`）。
2. **行走帧本身画得矮胖**：模型生成行走视频时把角色画成了"矮一截、宽一圈"
   （御厨 down 行走 212x266，宽高比 0.797；静态 220x371，0.593）。
   **重跑视频也没用**——实测重新生成 `front` 后比例依旧是 0.813。这不是抽帧问题，是生成模型的稳定偏好。

修法：新增 `tools/normalize-walk-sheet.py`，按方向算一次**非等比**归一化：
高度拉到静态身高（371），宽度拉到「静态宽高比 × 目标高」，所有帧共用同一组 (sx, sy)，脚底对齐、水平居中。
归一化后行走帧 371–377 高、宽高比与静态图一致（御厨 0.59 vs 0.60）。

副作用与已知问题：
- 御厨/门卫的 `left` 行走 sheet 原本整段抽坏（角色走出画面，帧内容顶满 224x224），
  用已归一化的 `_right` 水平镜像重建。
- `make-walk-sheet.py` 的闭合误差阈值是按 160 帧宽标定的，换 224 后同一条动作的像素误差被放大 1.4 倍，
  会误报；判断动作好坏要看渲染结果，不要只看这个数。

### 21. 御厨走路一闪一闪（2026-11-01 下午）
