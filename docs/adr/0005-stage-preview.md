# ADR 0005：舞台预览目录与测试后门

- 状态：已接受
- 日期：2026-10-24
- 决策者：universe-st
- 关联：`docs/STAGE-PREVIEW.md`、`src/dev/stage-catalog.ts`

## 背景

M0.9 只有「启动 → 标题 → 开幕 → 占位页」一条完整流程。后续会加入多章场景、CG、战斗；如果每次验收都从标题点起，会出现：

- 测试路径长、不可复现，QA 容易漏状态；
- 美术/策划无法单独看一张 CG 或一场战斗；
- 新场景容易依赖前置剧情/存档，形成隐性耦合；
- 自动化测试只能做很粗的端到端冒烟。

需要一个**代码可调用**的单点入口，并且规则要提前写死，避免每加一个场景就重新发明一次调试页。

## 决策

1. **单一类型化目录**：所有可预览内容登记在 `src/dev/stage-catalog.ts`，分 `scene` / `cg` / `battle` 三类；ID 是稳定验收契约，改名必须留 alias。
2. **单一启动器**：`launchStage(game, id, options)` 负责资源门禁、停旧场景、注入 `StageLaunchContext`、挂 HUD。URL、控制台、HUD 目录、代码全部走它。
3. **三个入口**：
   - `?stage=<id>`（Boot 中解析，跳过标题）；
   - `window.__AVM__.stages`（list/get/current/go/restart/title/url/hud）；
   - `launchStage()`（自动化/自定义工具）。
4. **通用 CG 查看器**：CG 只登记帧与 caption，不写专用场景。
5. **战斗契约沙盒**：`battle.sandbox` 先证明 seed/params/资源门禁/退出路径；真实战斗新增 `battle.*` 条目。
6. **预览 HUD 用 DOM**：可覆盖任意 Phaser 场景（包括尚未接入 UIScene 的战斗），不占设计空间、不抢输入焦点；用 `hud=0` 关闭。
7. **同包发布、默认常开**：单机无联网竞争，后门不构成作弊收益；不引入第二套 dev 构建，避免 Android 验收包与 Web 行为不一致。
8. **测试强制登记**：`stage-catalog.test.ts` 校验目录结构、模块 gate 同步、内容场景覆盖；新增场景不登记会让 `pnpm check` 失败。

## 后果

### 正面

- 任意内容单点打开，验收/截图/视频/缺陷复现成本大幅下降。
- 所有预览共用资源门禁，不会出现「调试页能跑、正式流程缺图」。
- seed + params 让战斗/演出可回放，给后续自动化留好接口。
- 新场景/CG/战斗的接入步骤固定，AI/协作者照文档即可。

### 负面 / 代价

- 目录、场景 key、模块表三处需要同步；已用单测降低漏登记风险，但仍需 code review。
- 场景必须容忍 `init(undefined)`，并处理 `preview` 不写存档的约束；早期场景要逐步补齐。
- 后门随包发布，目录标题可能剧透；需要控制标题措辞，未来若要剥离需单独实现构建开关。
- HUD 是 DOM，和 Phaser UI 不是一套主题；这是有意的工具边界。

## 备选方案

| 方案 | 拒绝原因 |
| --- | --- |
| 只做一个 dev-only 的「关卡选择」场景 | 仍然依赖场景列表；CG/战斗无法统一；且 Android 包行为与 Web 不一致。 |
| 每个场景自己解析 `?debug=` / 自建调试页 | 重复、易漂移，资源门禁和退出逻辑各写一套。 |
| 单独做 Storybook/静态预览站 | 与真实运行时分离，Phaser 场景/输入/资源行为不一致，维护成本高。 |
| 运行时动态扫描场景类自动生成目录 | Phaser 场景没有可靠的静态元数据；资源 gate/参数仍要手写，自动扫描只解决一半问题。 |
